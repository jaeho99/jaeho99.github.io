BowlingHub는 볼링장 운영에서 반복되는 회원, 점수, 모임과 이벤트 관리를 하나로 모은 Spring Boot 애플리케이션이다.

처음에는 회원과 점수를 관리하는 작은 프로젝트였지만, 실제 운영 흐름을 반영하면서 월간 랭킹, 모임 참가, 캡슐 상품 재고와 지급 이력, 회원·관리자 계정 관리까지 확장했다. Codex와 기능을 순서대로 구현하고 각 단계마다 테스트를 늘려갔다.

## 프로젝트 범위

핵심 도메인은 다음과 같다.

```text
BowlingHub
├─ 회원과 계정
├─ 게임 점수와 월간 랭킹
├─ 볼링 모임과 참가자
├─ 캡슐 이벤트·상품 재고·지급 이력
├─ 볼링장 정보
└─ 관리자 운영 화면
```

백엔드는 Java 21과 Spring Boot로 구현했다. 로컬 환경에서는 파일형 H2를 사용해 별도 DB 설치 없이 실행하고, 운영 프로필에서는 PostgreSQL로 전환한다. Flyway가 스키마 버전을 관리하며 Docker Compose와 PostgreSQL 백업 스크립트도 준비했다.

## 요청의 회원 ID를 믿지 않기

초기 API에서는 모임 생성과 참가 요청에 회원 ID를 받을 수 있었다. 하지만 사용자가 요청 값을 바꾸면 다른 회원 이름으로 모임을 만들거나 참가할 위험이 있다.

이를 개선해 로그인한 세션의 회원을 기준으로 처리하도록 별도 보호 API를 구성했다.

```text
변경 전: 요청 body의 memberId 사용
변경 후: 인증 세션 → 현재 회원 조회 → 생성자·참가자로 사용
```

클라이언트가 보내는 식별자를 그대로 신뢰하지 않고 서버가 인증 컨텍스트에서 주체를 결정하도록 바꾼 것이다. 이 원칙은 모임뿐 아니라 프로필과 비밀번호 변경에도 동일하게 적용했다.

## 회원과 관리자 계정 분리

관리자 계정을 환경변수의 평문 값으로 매번 비교하는 대신, 최초 실행 시 BCrypt로 암호화해 `admin_users` 테이블에 저장하도록 변경했다.

Flyway 마이그레이션은 다음처럼 단계적으로 추가했다.

- `V1`: 초기 도메인 스키마
- `V2`: 관리자 계정 테이블
- `V3`: 회원 활성 상태
- `V4`: 로그인 보호 정보

이미 적용된 SQL을 수정하지 않고 새 버전을 추가하므로 로컬과 운영 DB의 변경 이력을 일관되게 유지할 수 있다.

회원은 자신의 닉네임과 비밀번호를 변경할 수 있다. 관리자는 회원 비밀번호를 임시 비밀번호로 초기화하고, 회원 활성 상태와 운영 데이터를 관리한다.

## 점수와 캡슐 이벤트의 운영 흐름

관리자 화면에서는 게임 점수를 조회·수정·삭제하고 회원별 점수 이력을 확인할 수 있다. 점수 데이터는 월간 랭킹 계산으로 이어진다.

캡슐 이벤트에서는 상품 재고와 지급 이력이 함께 움직여야 한다.

```text
상품 지급 → 재고 감소 + 지급 이력 생성
지급 취소 → 지급 상태 취소 + 재고 복구
```

지급 취소에서 재고 복구를 빠뜨리면 실제 보유 수량과 시스템 값이 달라진다. 두 변경을 하나의 서비스 트랜잭션 안에서 처리하고, 재고가 없을 때는 명시적인 예외를 발생시키도록 구성했다.

## 기능을 늘릴수록 테스트도 늘리기

프로젝트 완료 여부를 감으로 판단하지 않기 위해 전체 클린 빌드와 테스트를 기준으로 삼았다. 최종 점검에서는 자동 테스트 47개가 모두 통과했고 실패·오류·건너뜀은 없었다.

테스트 범위에는 다음 내용이 포함된다.

- 회원 가입과 중복 검증
- 로그인 세션과 Spring Security 설정
- 회원·관리자 계정 변경
- 점수 관리와 랭킹
- 모임 생성·수정·참가 규칙
- 캡슐 재고와 지급 이력
- 홈페이지 API

Codex와 빠르게 기능을 추가할수록 회귀 오류의 가능성도 함께 커진다. 자동 테스트는 AI가 만든 코드를 신뢰하기 위한 장식이 아니라, 요구사항을 실행 가능한 형태로 고정하는 장치였다.

## 로컬과 운영 환경 분리

로컬에서는 H2 파일 DB로 빠르게 시작한다. 운영에서는 환경변수로 PostgreSQL과 관리자 초기 정보를 주입한다.

```text
local: H2 + 빠른 개발
prod: PostgreSQL + Flyway + Docker + Actuator
```

민감한 값은 저장소에 넣지 않고 환경변수로 전달한다. Actuator health endpoint로 상태를 확인하고, PowerShell 스크립트로 PostgreSQL 백업을 만들 수 있게 했다.

## Codex와 작업하며 지킨 원칙

한 번에 전체 시스템을 만들지 않고 운영 가치가 높은 순서로 기능을 완성했다.

1. 회원과 점수 기본 기능
2. 랭킹과 모임
3. 캡슐 이벤트와 재고
4. 관리자 운영 기능
5. 세션 기반 권한
6. 계정 관리와 로그인 보호
7. 운영 DB·마이그레이션·백업

각 단계에서 컴파일, 테스트, JavaScript 문법과 실제 HTTP 응답을 확인했다. AI가 코드를 빠르게 생성하더라도 **요구사항의 우선순위, 보안 경계와 완료 기준은 사람이 결정해야 한다**는 점을 배웠다.

## 남은 개선점

- 운영 서버와 HTTPS 실제 배포 검증
- Testcontainers를 이용한 PostgreSQL 통합 테스트
- 관리자 행위 감사 로그
- 랭킹 계산의 경계 조건과 성능 테스트
- CI에서 빌드·테스트·컨테이너 이미지 생성을 자동화

BowlingHub는 Codex와 만든 프로젝트 중 가장 큰 도메인과 테스트 범위를 가진다. 단순 CRUD를 넘어 권한, 상태 복구, 마이그레이션과 운영 준비까지 연결한 경험을 보여준다.
