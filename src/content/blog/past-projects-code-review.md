오래된 GitHub 저장소를 다시 여는 일은 조금 부담스럽다. 당시에는 최선이라고 생각한 코드에서 부족한 부분이 먼저 보이기 때문이다. 하지만 이직을 준비하며 과거 프로젝트를 다시 읽어보니, 무엇을 만들었는지보다 **이후 관점이 어떻게 달라졌는지**를 설명하는 것이 더 중요하다고 느꼈다.

이번에는 대표 팀 프로젝트인 MarketClip과 최근의 개인 프로젝트 저장소를 함께 살펴봤다.

## 2022년: 기능을 끝까지 연결한 MarketClip

MarketClip에서는 Spring Boot로 실시간 중고거래 서비스의 백엔드를 만들었다. 내가 담당한 범위는 WebSocket·Redis Pub/Sub 채팅과 거래 상태 관리였다.

이 프로젝트에서 가장 의미 있었던 경험은 여러 기술을 사용했다는 사실보다 하나의 사용자 행동이 여러 상태를 바꾸는 흐름을 구현한 것이다.

```text
거래 요청
├─ 상품: 판매 중 → 예약 중
├─ 판매자 화면: 요청 전송 상태
├─ 구매자 화면: 수락·거절 가능 상태
└─ 다른 구매자 화면: 상품 상태 갱신
```

당시에는 기능 완성을 위해 서비스 계층에 조회, 상태 변경과 이벤트 발행을 함께 작성했다. 지금은 이 구조에서 도메인 상태 전이와 실시간 알림을 분리해야 테스트와 변경이 쉬워진다는 점이 먼저 보인다.

## 이후: 학습 저장소가 늘었지만 설명은 부족했다

GitHub에는 Java, Spring, React, SQL, 보안, 알고리즘 등 다양한 학습 저장소가 남아 있다. 최근에는 영화 리뷰 개인 프로젝트를 통해 React와 백엔드 API를 함께 구성하고, JWT·댓글·별점·검색·캐시 등을 단계적으로 학습하려는 계획도 세웠다.

하지만 저장소를 다시 읽으며 한계도 발견했다.

- 목표와 기술 목록은 있지만 완료 조건이 구체적이지 않았다.
- 구현 전 계획과 실제 완료된 기능이 구분되지 않았다.
- 기능 선택 이유와 대안 비교가 부족했다.
- 테스트 결과와 성능 수치가 거의 남아 있지 않았다.
- 프로젝트가 길어질 때 범위를 줄이는 기준이 없었다.

기술 키워드를 많이 적는 것만으로는 경험이 설명되지 않는다. 예를 들어 “Redis 캐시 적용”보다 다음 내용이 있어야 한다.

```text
문제: 동일한 상품 상세 조회가 반복되어 DB 부하가 예상됨
가설: 읽기 빈도가 높고 수정이 적으므로 캐시가 유효함
선택: Cache-Aside + 24시간 TTL
검증: 적용 전후 p95 응답 시간과 DB 쿼리 수 비교
회고: 수정 시 eviction 누락 여부와 stale data 허용 범위
```

## 다음 프로젝트에서 바꿀 방식

### 1. MVP의 완료 조건부터 정한다

“영화 리뷰 사이트 만들기” 대신 사용자 관점의 완료 조건을 작성한다.

- 사용자가 회원가입하고 로그인할 수 있다.
- 영화를 조회하고 리뷰와 별점을 작성할 수 있다.
- 자신의 리뷰를 수정·삭제할 수 있다.
- 핵심 API에 자동화 테스트가 있다.
- 운영 주소와 API 문서가 공개되어 있다.

이 조건을 만족한 뒤 검색, 소셜 로그인과 캐시를 추가한다. 학습하고 싶은 기술이 MVP 일정을 끌고 가지 않도록 한다.

### 2. 계획과 완료를 분리한다

README에는 `Planned`, `In progress`, `Done`을 구분한다. 아직 구현하지 않은 기술을 사용 기술처럼 보이게 적지 않는다.

### 3. 의사결정 기록을 남긴다

중요한 선택은 짧은 ADR 형태로 기록한다.

```text
Context: 어떤 문제가 있었는가
Decision: 무엇을 선택했는가
Alternatives: 어떤 대안을 비교했는가
Consequences: 얻은 것과 감수한 것은 무엇인가
```

### 4. 검증 가능한 결과를 만든다

테스트 통과 여부, API 응답 시간, 쿼리 수, 배포 성공 여부처럼 확인 가능한 결과를 남긴다. 수치가 없다면 성능이 개선됐다고 단정하지 않는다.

### 5. 회고를 기능 단위로 작성한다

프로젝트가 끝난 뒤 한 번에 회고하려 하면 세부 판단을 잊는다. 인증, 검색, 캐시처럼 기능 하나가 끝날 때마다 문제와 선택을 기록한다.

## 과거 코드는 성장의 기준선이다

과거 프로젝트의 부족한 점을 숨기기보다, 당시의 제약과 지금의 개선 방향을 설명할 수 있는 것이 더 좋은 포트폴리오라고 생각한다.

MarketClip은 실시간 상태 관리 경험을 보여준다. 최근의 학습 저장소들은 관심 기술과 학습 방향을 보여준다. 이제 필요한 것은 둘을 연결해 **작은 범위를 완성하고, 선택의 근거와 검증 결과를 남기는 습관**이다.

앞으로 이 블로그도 기술 요약보다 실제 문제 해결 과정을 중심으로 채워가려고 한다.
