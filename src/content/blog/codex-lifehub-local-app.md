생활 기록은 여러 앱에 흩어지기 쉽다. 청소 주기, 자산과 지출, 운동 기록, 냉장고 식재료와 레시피를 한 화면에서 관리하기 위해 LifeHub를 만들었다.

처음부터 외부 서비스로 배포하는 대신 **내 Windows PC 한 대에서만 사용하는 로컬 웹 애플리케이션**으로 범위를 제한했다. Codex와 함께 요구사항을 도메인으로 나누고, Spring Boot·React·PostgreSQL을 연결했다.

## 왜 로컬 웹앱인가

데이터는 PC를 재시작해도 남아야 하지만 인터넷 공개, 다중 사용자와 회원가입은 필요하지 않았다.

브라우저 UI는 데스크톱 앱처럼 사용하기 편하고, Spring Boot와 PostgreSQL은 이후 기능을 추가하기 좋다. 반면 외부 배포를 생략하면 인증, 도메인, HTTPS와 서버 운영을 당장 해결하지 않아도 된다.

```text
React + TypeScript
       ↓ REST API
Spring Boot 3.3
       ↓ JPA
PostgreSQL
```

## 기능을 도메인으로 나누기

백엔드는 기능별 패키지로 구성했다.

| 도메인 | 주요 기능 |
|---|---|
| dashboard | 오늘의 요약 정보 |
| cleaning | 청소 항목과 완료 이력 |
| finance | 자산·수입·지출과 총액 계산 |
| workout | 운동 기록 |
| ingredient | 식재료 수량과 소비 이력 |
| recipe | 레시피와 필요 재료 |
| common | CORS와 공통 예외 처리 |

처음부터 모든 기능을 하나의 서비스에 넣지 않고 도메인별 Controller, Entity와 Repository를 분리했다. 개인용 앱이라도 기능이 늘어날수록 경계가 필요하기 때문이다.

## 자산 총액을 서버에서 계산하기

자산 관리 화면에는 등록 자산뿐 아니라 수입과 지출이 반영된 현재 금액이 필요했다.

```text
현재 총 금액 = 등록 자산 합계 + 누적 수입 - 누적 지출
```

프런트엔드에서 기존 목록을 더하는 대신 서버의 요약 API가 계산하도록 했다. 기록이 추가되거나 삭제될 때 서버에서 다시 조회하므로 계산 기준을 한곳에 둘 수 있다.

수입과 지출 카테고리는 자유 입력 대신 선택형으로 바꿨다. 데이터가 쌓인 뒤 카테고리별 통계를 만들려면 같은 의미의 값이 여러 철자로 저장되는 문제를 막아야 한다.

## 실행 환경도 제품의 일부였다

기능 코드보다 예상보다 많은 시간이 든 부분은 Windows 실행 환경이었다.

- PostgreSQL은 설치됐지만 `psql.exe`가 PATH에 없었다.
- 시스템 Java 버전과 프로젝트 요구 버전이 달랐다.
- 별도 Gradle 설치가 없었다.
- 8080 포트를 다른 Java 애플리케이션이 사용 중이었다.
- 배치 파일의 상태 검사 구문이 정상 실행을 실패로 표시했다.

이를 해결하기 위해 `start.bat`, `stop.bat`, `setup-runtime.bat`을 만들었다.

`start.bat`은 PostgreSQL 실행 파일을 찾아 연결을 확인하고, `lifehub` DB가 없다면 생성한다. 백엔드는 충돌을 피해 18080 포트를 사용하고 프런트엔드는 5173에서 실행한다. 프로젝트 전용 Gradle도 준비해 시스템 설정 의존성을 줄였다.

여기서 얻은 교훈은 **로컬 앱도 다른 사람이 실행할 수 있어야 완성된 프로젝트**라는 점이다. IDE에서 실행되는 것만으로는 부족하다.

## Codex와 진단한 방식

오류 메시지를 그대로 고치는 대신 로그와 실제 상태를 분리해 확인했다.

예를 들어 `[ERROR] LifeHub failed to start`가 표시됐을 때 백엔드 로그, 프런트엔드 로그, 포트와 HTTP 응답을 확인했다. 실제 애플리케이션은 정상 실행 중이었고, 문제는 배치 파일의 상태 검사였다.

Codex가 명령 실행과 로그 비교를 빠르게 수행했지만, 중요한 판단 기준은 다음과 같았다.

1. 오류 메시지가 실제 장애를 의미하는가?
2. 백엔드와 프런트엔드 중 어느 프로세스가 실패했는가?
3. 코드, 환경, 실행 스크립트 중 어디에 원인이 있는가?
4. 기존에 실행 중인 사용자 프로그램을 종료하지 않고 해결할 수 있는가?

## 검증과 한계

프런트엔드 TypeScript 빌드와 백엔드 테스트를 통과했고, PostgreSQL 연결과 HTTP 200 응답을 확인했다.

현재 버전은 로컬 1인 사용을 전제로 하므로 로그인과 외부 접근 보호는 없다. 외부 배포로 확장한다면 인증·권한, Flyway 기반 명시적 마이그레이션, 백업과 HTTPS가 필요하다. 현재의 `ddl-auto: update`도 운영 환경에서는 변경해야 한다.

LifeHub를 만들며 기능 구현뿐 아니라 실행 환경과 운영 범위를 설계하는 경험을 얻었다. 특히 문제를 재현하고 로그로 실제 상태를 확인하는 습관이 가장 큰 결과였다.
