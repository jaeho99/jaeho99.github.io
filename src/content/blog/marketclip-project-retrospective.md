MarketClip은 짧은 영상으로 상품을 살펴보고 판매자와 실시간으로 대화할 수 있는 중고거래 서비스다. 2022년 6월부터 8월까지 프론트엔드 2명, 백엔드 3명, 디자이너 2명이 함께 만들었다.

나는 백엔드에서 **WebSocket과 Redis Pub/Sub을 이용한 실시간 채팅, 채팅방 관리, 거래 상태 변경 기능**을 담당했다. 시간이 지난 프로젝트지만, 지금 다시 코드를 읽어보니 당시 어떤 문제를 풀려고 했는지와 다음에는 무엇을 다르게 할지가 더 분명하게 보였다.

## 서비스에서 풀어야 했던 문제

MarketClip의 채팅은 메시지만 주고받는 기능이 아니었다. 하나의 상품에 여러 구매자가 문의할 수 있고, 판매자는 그중 한 명에게 거래를 제안할 수 있어야 했다. 거래 진행에 따라 상품과 채팅 화면도 함께 바뀌어야 했다.

```text
판매 중 → 거래 요청 → 예약 중 → 거래 완료
                     ↘ 거래 거절 → 판매 중
```

따라서 백엔드에는 다음 책임이 필요했다.

- 상품별 구매자·판매자 채팅방 생성
- 실시간 메시지 전송과 메시지 영속화
- 읽지 않은 메시지 수와 마지막 메시지 조회
- 거래 요청·수락·거절에 따른 상품 상태 변경
- 거래 상대가 아닌 채팅방에도 상태 갱신 이벤트 전달
- 채팅방 퇴장 시 거래 상태와 후기 대기 상태 복구

## 기술 구성

백엔드는 Java와 Spring Boot를 중심으로 구성했다. 데이터는 MySQL과 JPA로 관리했고, 동적 상품 검색에는 QueryDSL을 사용했다. Redis는 캐시와 실시간 채팅의 Pub/Sub 브로커로 활용했다.

| 영역 | 기술 |
|---|---|
| API·도메인 | Java, Spring Boot, JPA, QueryDSL |
| 인증 | Spring Security, JWT, OAuth 2.0 |
| 실시간 통신 | WebSocket, STOMP, Redis Pub/Sub |
| 데이터 | MySQL, Redis |
| 파일 | Amazon S3 |
| 운영 | EC2, RDS, Nginx, GitHub Actions |

## 내가 담당한 기능

### 실시간 채팅

클라이언트가 STOMP 엔드포인트로 메시지를 보내면 서버는 해당 채팅방의 Redis 토픽에 메시지를 발행했다. Redis 구독자는 메시지를 역직렬화한 뒤 WebSocket 구독자에게 전달하고 DB에 저장했다.

이 구조를 통해 메시지 발행과 WebSocket 전달 책임을 분리할 수 있었다. 자세한 구현과 고민은 [Redis Pub/Sub 채팅 구현기](/posts/marketclip-redis-chat/)에 별도로 정리했다.

### 채팅방과 읽음 상태

채팅방 목록에서는 마지막 메시지, 안 읽은 메시지 수, 상대방 정보와 상품 상태가 함께 필요했다. 메시지 조회 시에는 상대가 보낸 메시지의 읽음 상태를 변경하도록 구현했다.

판매자와 구매자는 같은 채팅방을 보지만 수행할 수 있는 행동이 달랐다. 그래서 상품 상태와 현재 사용자의 역할을 조합해 화면에 전달할 거래 상태를 계산했다.

### 거래 상태 관리

판매자가 거래를 요청하면 상품을 예약 상태로 바꾸고 구매자에게 수락·거절 이벤트를 전달했다. 거래가 완료되면 나머지 구매자들의 채팅 목록도 갱신해야 했다.

이 과정에서 배운 것은 **DB의 상품 상태만 변경해서는 실시간 화면의 일관성이 보장되지 않는다**는 점이다. 도메인 상태 변경과 사용자별 알림 이벤트를 하나의 흐름으로 함께 설계해야 했다.

## 함께 구현된 주요 기능

팀 전체로는 다음 기능도 구현했다.

- JWT·Refresh Token 기반 로그인과 소셜 로그인
- 다중 카테고리 필터와 정렬을 지원하는 QueryDSL 동적 조회
- 상품 상세·구매 목록·판매 목록 등에 Redis 캐시 적용
- 이미지 업로드와 S3 저장
- 만료 이메일과 사용되지 않는 S3 파일을 정리하는 스케줄러
- GitHub Actions 기반 배포 자동화

특히 상품 이미지 수정에서는 기존 이미지와 새 이미지의 순서를 한 요청에서 다루기 어려웠다. 업로드 API가 먼저 S3 URL을 반환하고, 게시글 API는 URL의 순서만 관리하도록 책임을 분리했다. 대신 게시글에 연결되지 않은 파일이 남을 수 있어 스케줄러로 정리하는 후속 작업이 필요했다.

## 지금 다시 본 기술 부채

작동하는 기능을 만드는 데 집중한 만큼 개선할 부분도 명확하다.

첫째, 거래 요청과 채팅방 퇴장 같은 이벤트를 `TRADE`, `CHAT_REMOVE` 등의 문자열로 구분했다. 빠르게 구현하기에는 편했지만 이벤트 종류가 늘수록 분기문이 커진다. 지금이라면 이벤트 타입과 payload를 명확하게 정의한 메시지 객체로 분리할 것이다.

둘째, 서비스 코드가 조회·상태 계산·이벤트 발행을 함께 담당한다. 거래 상태 전이를 별도의 도메인 서비스로 분리하고, 상태별 허용 행동을 테스트로 고정하면 변경에 더 안전하다.

셋째, 캐시를 적용했다는 사실보다 **왜 그 TTL을 선택했고 실제 응답 시간이 얼마나 바뀌었는지** 측정 자료가 부족하다. 다음 프로젝트에서는 적용 전후 지표와 캐시 적중률을 반드시 남기려고 한다.

## 이 프로젝트에서 얻은 것

MarketClip을 통해 CRUD를 넘어 상태와 실시간 이벤트가 결합된 기능을 처음 끝까지 구현했다. 특히 다음 세 가지가 이후 개발 방식에 영향을 줬다.

1. 실시간 기능에서도 최종 데이터의 기준은 DB와 도메인 상태여야 한다.
2. 이벤트 이름과 payload는 API 계약처럼 관리해야 한다.
3. 기술을 사용했다는 사실보다 문제와 선택 이유, 검증 결과를 기록해야 한다.

완벽한 코드는 아니지만, 지금의 관점으로 과거 구현을 설명하고 개선점을 찾는 것 역시 중요한 개발 경험이라고 생각한다.
